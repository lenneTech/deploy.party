## Update

```bash
cd /var/opt/deploy-party
sh update.sh
```

The script pulls the latest images of the app and the API and redeploys the stack. It needs no parameters.

Run system updates of the server separately, see [Maintenance](./6.server/4.maintenance.md).

## Once for older installations

### Registry only on localhost

New installations bind the local registry to `127.0.0.1`. Installations from before that make it reachable on all
interfaces. Switch an existing installation once:

```bash
cd /var/opt/deploy-party
curl -fsSL https://raw.githubusercontent.com/lenneTech/deploy.party/main/secure-registry.sh -o secure-registry.sh
bash secure-registry.sh --check   # exit code 2: still public
bash secure-registry.sh           # switch; keeps the data volume, rolls back by itself on any difference
bash secure-registry.sh --cleanup # after the next successful deploy: remove the stopped old container
```

The script refuses on a multi-node swarm (other nodes pull from this registry) and while a push is running.
`--rollback` restores the previous container. Once `secure-registry.sh` sits next to `update.sh`, every update runs it
as well.

### Build files from the container settings

With `NSC__REFRESH_BUILD_FILES=true` every build writes `Dockerfile` and `docker-compose.yml` from the container
settings first, so a changed setting goes live with the next build. New installations set it. For an existing
installation, check first what the first builds would change:

```bash
docker exec $(docker ps -qf name=deploy-party_api) node dist/src/server/scripts/build-files-drift.js
```

One line per container: `UNCHANGED`, `EXPECTED` (only the health check, the update and rollback settings, or a
basic-auth label in the new hash format) or `OTHER` with the keys that differ, never the values. Settle every `OTHER`
first: settings that were changed but never deployed, or a file edited by hand on the server. Then add
`NSC__REFRESH_BUILD_FILES=true` to the `.env` and run `update.sh`.

### Webhook secret

Every source has its own webhook secret, which GitLab sends as `X-Gitlab-Token`; hooks created from the UI carry it.
New installations check it (`NSC__WEBHOOK_TOKEN_MODE=enforce`). For an existing installation:

1. Run `update.sh` (a migration creates the secrets), set `NSC__WEBHOOK_TOKEN_MODE=report` and run `update.sh` again.
2. Put the secrets into the existing hooks. The GitLab token goes in on stdin and needs Maintainer rights with scope
   `api`; the script prints only project and hook ids:
   ```bash
   printf '%s\n' "$GITLAB_ADMIN_TOKEN" | docker exec -i $(docker ps -qf name=deploy-party_api) \
     node dist/src/server/scripts/webhook-secret-hooks.js --gitlab-host gitlab.example.com          # dry run
   printf '%s\n' "$GITLAB_ADMIN_TOKEN" | docker exec -i $(docker ps -qf name=deploy-party_api) \
     node dist/src/server/scripts/webhook-secret-hooks.js --gitlab-host gitlab.example.com --apply
   ```
3. Watch the API log for `came with no X-Gitlab-Token` or `a wrong X-Gitlab-Token`, for example CI jobs that call the
   webhook themselves. When nothing shows up any more, set `NSC__WEBHOOK_TOKEN_MODE=enforce` and run `update.sh`.

### Swagger

Swagger UI and the OpenAPI document of the API are off by default. To switch them on for an instance, set
`NSC__SWAGGER=true` and run `update.sh`.

### Traefik v3

deploy.party uses Traefik v3. An installation still on Traefik v2 migrates with `upgrade-traefik-v3.sh`; the steps,
the rollback and the troubleshooting are in
[MIGRATION.md](https://github.com/lenneTech/deploy.party/blob/main/MIGRATION.md).
